# ADR-0001：Talkwire 的总体架构与 v1 范围

- 状态：已采纳
- 日期：2026-10-24
- 依据：《Talkwire 详细开发计划》（https://claude.ai/artifact/Eh89avD5BQyVK1Urfz7Lss）

## 背景

小桃子的自研 IM 已在生产运行，但服务端核心是一个 5003 行的 `hub.go`，与宿主业务（积分、红包、通话计费、群 AI）硬编码耦合；Android 客户端的连接层是 3012 行的单例并直接调用仓储与通知。要让新项目复用这套能力，必须把通用部分抽成框架，同时保证原项目将来能无损迁移过来。

## 决定

1. **许可证**：核心 Apache-2.0。链接 libsignal（AGPLv3）的 E2EE 客户端模块独立发布并标注 AGPLv3；服务端 E2EE 只存转不透明密文，不链接 libsignal，仍为 Apache-2.0。
2. **平台**：v1 交付 Go 服务端、Node 宿主 SDK、Android、iOS、Web 三端 SDK。协议规范按“另一个团队照着就能实现客户端”的标准编写，Web 先行验证这一点。
3. **多端同时在线**：v1 支持同一账号多个设备同时在线（登录携带设备 id；同一设备重连才顶替）。E2EE 多设备不在 v1。
4. **协议 v1 冻结，只加不改**：字段名、action 名、应答码与现网逐位一致；改进以新增字段、新增 action 的方式进入，并由登录应答里的协议版本协商。
5. **清空语义冻结**：清空会话会把该会话所有成员的消息从服务端物理删除并推进水位，不在 v1 提供“只清自己”。
6. **存储**：v1 只支持 PostgreSQL。迁移基线 `0001_baseline` 从原版服务在空库上建出的结构导出，保证现网库可直接执行。
7. **重构方式**：先把原版服务原样搬入并证明逐帧一致，再逐块替换；每一步之后一致性测试必须全绿。以原版服务（源提交 `33e23250`）为差分测试的参照。
8. **服务端结构**：核心保持单个 Go 包、按职责拆文件；只有可选模块（E2EE、通话、机器人钩子、扫码入群）和宿主适配层成为独立包。
9. **宿主边界**：服务端通过身份、uid 映射、关系策略、资料、媒体、配置六个接口与宿主交互；提供 HTTP 适配器（与现网契约一致）和进程内的 standalone 实现。
10. **安全修正**：用户令牌只接受 `type=access`（现网会接受刷新、代理、管理员令牌），迁移期提供默认关闭的兼容开关。

## 后果

- 三端与宿主 SDK 可在服务端核心通过一致性闸门（G1）后并行开发。
- iOS 开发依赖 macOS 环境；竞态检测依赖 C 工具链或 Linux CI。
- 多端在线让服务端连接表、在线状态、离线补投与推送去重都要改造，Phase 1 增加约 10–15 人日。
