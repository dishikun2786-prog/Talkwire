# loadtest

压测工具（计划 9.3）：很多用户同时连上一个 ImKit 服务端，登录、两两组成单聊、按人数分群，再以固定速率发消息，测量登录耗时、`pub` 应答耗时、单聊与群消息送达耗时，并统计丢失。独立的 Go 模块，依赖与 `tools/conformance` 相同（gorilla/websocket、golang-jwt）。

```bash
cd tools/loadtest
LOADTEST_JWT_SECRET=<服务端的 JWT_SECRET> go run . -url ws://127.0.0.1:6062/ws/im -users 1000 -group-size 50 -rate 1 -duration 60s
```

| 参数 | 默认 | 作用 |
| --- | --- | --- |
| `-users` | 100 | 用户数，每人一条连接 |
| `-group-size` | 10 | 每个群的人数；0 不建群。用户同时两两配对发单聊 |
| `-rate` | 1 | 每人每秒发几条，单聊与群轮流 |
| `-duration` | 30s | 发多久 |
| `-ramp` | 10s | 连接在这段时间里均匀建立 |
| `-drain` | 10s | 停发之后最多再等多久收尾 |
| `-max-loss` | 0 | 丢失超过这个比例就以 1 退出 |
| `-json` | 不写 | 另把结果写成 JSON |
| `-strict-token` | true | 签 strict 档要求的令牌（`type=access`、`role=app_user`）；对 legacy 档也能用 |

每次运行用新的用户 id 前缀，互不影响。消息正文带发送时刻，接收方据此算送达耗时，所以压测端各进程要在同一台机器上，或时钟同步。

## 服务端怎么配

- 宿主要让所有用户互为好友：用 standalone 宿主（`IMKIT_HOST_MODE=standalone`）的默认 `allow-all`。
- 发送频率默认每人 10 秒 20 条，`-rate` 超过 2 时要在运行配置里调高；建大群时把人数上限调到 `-group-size` 以上。standalone 宿主的配置文件：

  ```json
  {"relations": "allow-all", "runtimeConfig": {"publishRateLimitPer10s": 100000, "maxMembers": 500, "readReceiptEnabled": true}}
  ```

- 数据库用一个可以随便写的库：每条消息都入库。

## 判定

全部用户登录成功、全部群建成、每条消息都有应答、没有连接被服务端中途断开，并且丢失不超过 `-max-loss`，才以 0 退出。服务端发现某个连接的发送队列满了（客户端读得太慢）会断开它，让它重连后补拉；这在报告里算“closed early”，被断开的连接收不到的消息算丢失。

## 本机试跑（2026-10-25）

Windows 11，i7-8700（12 个逻辑核）、16 GB；服务端、PostgreSQL 17 与压测端在**同一台机器**上，strict 档，standalone 宿主。下面的数字只说明工具能用、服务端在这个量级下行为正确，不代表服务端的上限：压测端与服务端抢 CPU，而网络是本机回环。

| 用户 | 群 | 每人每秒 | 发送 | 送达 | 丢失 | ack p50 / p99 | 群送达 p50 / p99 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 50 | 5 个 × 10 人 | 1 | 451 | 2 251 | 0 | 3.2 / 13.1 ms | 2.6 / 10.7 ms |
| 1000 | 20 个 × 50 人 | 1 | 29 003（967/s） | 725 051（24 165/s） | 0 | 2.1 / 2.9 ms | 1.6 / 2.7 ms |
| 1000 | 4 个 × 250 人 | 1 | 18 608（863/s） | 2 315 748（107 349/s） | 7 017（0.3%） | 1 034 / 6 537 ms | 1 007 / 6 464 ms |

最后一行已经饱和：每秒约 500 条群消息、每条发给 249 人。第一次跑这一档时压测端把每帧解码成通用的 map，自己先跟不上，服务端因此断开了 303 个读得慢的连接、丢了 25%；改成只解码需要的字段后，断开降到 7 个、丢失降到 0.3%。剩下的饱和是服务端的还是压测端的，同一台机器上分不出来。
